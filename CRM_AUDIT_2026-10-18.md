# OrderLedger: settings incident and essential CRM gaps

## Live incident

Website: https://orderledger-eight.vercel.app/

Configured API: https://orderledger-api.onrender.com

The deployed frontend and backend are incompatible. Public frontend assets contain the new settings and provider-connection interface, while the active API still implements the older contract.

Verified on 18 October with a separate, empty diagnostic business:

- Registration and `GET /api/business` return a business without `settings`.
- `PATCH /api/business` with the current frontend's complete form returns **500 / Internal server error**.
- A settings-only PATCH returns 200 but does not persist or return settings. HTTP success alone is therefore insufficient verification.
- Authenticated `GET /api/business/connections` returns **404 / Cannot GET**.
- `/health` returns 200, but the older implementation does not identify settings support.

No customer, order, invoice or payment records were created or modified by these diagnostic requests. The diagnostic workspace is named `Settings diagnostic …`; its credentials remain in OS temporary storage, outside Git.

The immediate repair is to deploy the current backend, including migrations 004 and 005, to the existing Render service. GitHub already contains those implementations. The reason Render retained the older build (deployment failure, disabled automatic deployment, or different deployment settings) requires Render deployment/log access; it cannot be determined from the public API alone.

### Deployment checks

For the existing Render service, check repository `Arman-Khan-24/vendor-management-system-core`, branch `main`, root directory `backend`, build command `npm ci && npm run build`, and start command `npm start`. Preserve the existing database connection and stable JWT secret. Production startup requires a valid configured secret and stops on migration failure.

After deployment, require all of these before declaring the incident resolved:

1. `/health` returns `status: "ok"` and `apiVersion: 2`.
2. An authenticated business response includes normalized `settings`.
3. A theme update survives a subsequent GET and browser reload.
4. The authenticated Connections endpoint returns both provider slots, with saved-key flags but no keys.
5. The Vercel interface can save profile, appearance, catalog, billing and feature settings against that API.

This document does not claim the Render redeployment has happened. Record the deployed revision and live verification when access is available.

## Additional defects repaired in this revision

| Defect | Repair |
| --- | --- |
| Validation messages crashed because the API returns a string field path, while the frontend called `.join()` on it | Accept string and array paths and show the actual field error. Reproduced before the fix with a too-long tax ID. |
| Saving appearance sent the complete old business form and could overwrite independent changes from another tab | Send only changed fields, including within each settings section. |
| Provider drafts disappeared when changing settings sections | Preserve the Connections form and guard navigation/reload for unsaved business, provider and server-address edits. |
| A provider save could overwrite the other slot's more recent configuration | Send only changed provider fields; keep saved keys untouched unless explicitly changed or removed. |
| Server tests accepted a readable old API as a working current connection | Check database readiness and the supported API version. Proxy `/health` in local development as well as `/api`. |
| An older API could return 200 while ignoring settings | Block settings saves when the loaded business lacks settings; reject a save response without settings. |
| The API address was hard to discover, especially with horizontally scrolling mobile settings tabs | Add a visible **Server & API settings** action and a connection shortcut after save errors. |
| Tax-ID input allowed more characters than the server accepts | Match the server's 60-character limit. |

## What is still essential

This product currently supports a wholesale customer ledger: catalog, customers, orders, invoices, collections, statements and reports. It does not yet cover the full customer relationship or wholesale operations lifecycle. The following priorities come from the active routes, repositories and interface, rather than the older phase-completion claims.

| Priority | Required work | Current evidence and acceptance target |
| --- | --- | --- |
| **P0 — before relying on the live service** | Reliable deployment and recovery | Resolve the incident above. Confirm scheduled database backups and actually restore one to a separate database. Hosting backup/alert configuration is unverified, not proven absent. Alert on API/readiness failure and test a save after releases. |
| **P0 — before real financial use** | Corrections, cancellation, returns, credit notes and payment reversals | Order status only advances Received → Packed → Delivered; payment routes create/list; no correction/refund lifecycle exists. A mistaken payment or returned item must be correctable through an auditable compensating entry, with balances and reports reconciled. Do not silently edit or delete issued financial history. |
| **P0 — account reliability** | Password recovery, login throttling and revocable sessions | The active auth routes expose registration/login/me; authentication trusts the JWT until expiry. Add owner recovery, abuse limits and session revocation. Registration also creates business, seeded products and owner in separate operations; put them in one transaction and protect concurrent email registration before scaling signup. See `backend/src/services/auth.service.ts` and `repositories/user.repo.ts`. |
| **P1 — multi-person use** | Staff invitation, permissions and activity history | Role checks exist, but team invitations/removal/role management are not exposed as a complete owner workflow. Add customer/financial change history with actor, time and reason; order-status history alone is insufficient. Verify revoked users immediately lose access. |
| **P1 — make it a CRM** | Customer contacts, notes, follow-ups and a unified timeline | Customer records mainly hold name, phone and payment terms. Add billing/delivery addresses, contact people, assigned staff, notes, next follow-up date and a timeline combining conversations, orders and collections. A due follow-up list should answer whom the team needs to contact today. |
| **P1 — collection workflow** | Payment detail/receipt and collection follow-ups | Statements and overdue reports exist. Add a receipt/detail view showing allocations, customer credit and correction history, plus promised-payment dates and collection tasks. Scheduled message delivery can wait for the explicitly deferred integration. |
| **P1 — safe retries and onboarding** | Idempotent order/payment submission; validated imports and opening balances | Status transitions are retry-safe, but order/payment creation has no client idempotency key. A lost response followed by retry can create duplicates. CSV export exists; validated import with preview, duplicate handling and reconciled opening balances does not. |
| **P1 — local accounting rules** | Business timezone and the required tax invoice format | Reporting boundaries use UTC. Add a business timezone and verify midnight boundaries for India. Current tax is one percentage; if clients require GST invoices, scope GSTIN, HSN/SAC, place of supply and CGST/SGST/IGST explicitly before using it for compliant billing. |
| **P1 when selling tracked stock** | Inventory, suppliers, purchases and partial fulfilment | There is a catalog, not a stock ledger. Add receipts, deliveries, returns/adjustments and available stock with an audit trail; support partial deliveries/backorders if required by the wholesale business. Do not promise inventory management from catalog quantities alone. |
| **P2 — larger accounts** | Server-side search/pagination and role-specific screens | Current UI renders 24 records at a time but loads all records in 500-record batches. Move search/filtering to the API before ledgers become large. Delivery users also need a focused permitted workflow rather than screens whose APIs reject their role. |

Recommended build order: restore the deployed settings workflow; establish recovery and financial corrections; harden account/team access; add customer follow-ups and collection detail; then imports, local accounting and inventory according to the first client's requirements.

WhatsApp and live AI ingestion remain deferred. They are not needed to make the manual CRM reliable, and stored provider configuration does not activate them.
